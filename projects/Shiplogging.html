Shiplogging

Play as a worker at a signal station, recording some information about passing ships by communicating with them using international maritime signal flags.

Made by me in 3 days for Ludum Dare 59 Jam. You can play it here.

Game concept

The theme of the jam is Signal. I came up with 2 ideas. One of them is a stealth game, with a need to launch a signal flare on extraction point to be rescued. The other involves ships with international maritime signal flags. I decided to go with the second idea as I find that more interesting, and I think that other people will too since international maritime signal flags is not commonly known.

Implementation

I decided to use Godot since it is my favourite engine and I can start with my project template.

Ship data generation

I wanted the ships to have an identifying code, origin and desination ports, as well as estimated remaining voyage time.

The code is split into 2 parts, the first is 1 or 2 random letters in between A to Z, and the second is simply a random number in between 1 to 99. It is possible that the same code can be generated again, which in that case the code is simply regenerated until it is unique.

To ensure that both origin and destination ports are unique, the origin port is popped from a duplicated array of ports, before having the destination port picked.

From my crude research, I learned that a ship from Europe will take about 30 days to reach Melaka. This allows the unit for estimated remaining voyage time to be days, which I think is perfect when shown in flags.

Scoring

I wanted the score to be based on how many ships with the correct data recorded.

I first created an entry, which is 3 inputs for non-code ship data surrounded by labels. The ship code is reflected in one of the labels to be used as a guide on which entry corresponds to which ship. The inputs and labels are all children of a container that arranges them horizontally. The entries in turn are all children of a container that arranges them vertically.

1 score is awarded if all text within an entry's inputs matches exactly with the corresponding ship data text.

Ship spawning and movement

There can be up to 3 ships on screen at one time, and they can come from the left or right. For simplicity, I want the ships to move from one side of the screen to the other after spawning.

I decided to represent the route a ship will take via a class. It will contain 2 markers, which can be visualised more easily when changing their position in the editor. I wanted the route to be able to be occupied such that there can only be 1 ship moving in it. An area collider is used to detect when the ship reaches the end location, making a route vacant.

The ships will spawn on a timer. It loops by default, but it uses the same set wait time. I wanted some variation in said time, so I manually start the timer with said time randomised each time the timer ends. An array of vacant routes is used to determine whether a ship should spawn, 1 to be randomly popped if so. This is why instead of using a boolean variable to represent if a route is vacant, I decided to emit a signal when it does so said route can be appended into the aforementioned array.

When a ship first occupies a route, it is rotated to face the end location. Every physics frame, it is being moved forward, calculated using transform.basis.z (facing backwards) and -1 (inverts direction, so now facing forwards). After a route is vacant, the ship's data is still required for score calculation even though it is no longer seen by the player, so it is disabled instead of freed.

Flag rack

I first created a script that stores all the flag textures via a dictionary with their corresponding characters being the keys. The script is then made an autoload so it can be accessed by anything. In hindsight, making it a static class instead is better since the script only stores the dictionary and does nothing else. An autoload is only needed when the game state will be modified, such as modifying nodes or using signals.

I wanted the inputting of message to be similar to using a keyboard but pressing buttons instead of typing on keyboard. Pressing on flag buttons will input a character, while there will be 2 buttons for removing the last character and sending the message respectively.

In the flag rack, all flag buttons are arranged using containers. As such, when the buttons are selected to have their respective flag texture and character set, find_children() which returns all descendants is used instead of the usual get_children() that only returns immediate children. It should be noted that it is assumed that the number of flag buttons matches the number of characters. If there are less flag buttons, not every character is represented; if there are more, an error will be thrown. Since there will always be 36 characters (26 uppercase alphabets and 10 digits), this is not really an issue.

The request message is stored internally and displayed to the player as a line of flags. The maximum length of the message can be changed by adding more flag TextureRects into the container for them in the editor.

Communication with ships

I decided to decode the message by first finding a valid request code in it, which will be erased if it exists. If the erased message is one of the ship codes, the request code is passed to the corresponding ship.

As I am writing this article I realised that this implementation means players are not required to input the request code after the ship code as I intended to. This is because there is no check on whether the request code comes after the ship code. A possible fix is to first check if the ship code exists and it is in front before passing the message with the ship code erased to the corresponding ship, which already checks the passed string anyways.

The ship's code is always displayed while the other data is displayed if requested. They are displayed in flags, which are Sprite3Ds.
